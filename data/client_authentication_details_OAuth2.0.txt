In OAuth 2.0, client authentication refers to the process where a confidential client (a server-side application that can securely store a secret) proves its identity to the Authorization Server when requesting an access token. Public clients (like single-page apps or mobile apps) cannot secure credentials and typically do not authenticate this way. [1, 2]
The core specification (RFC 6749) and subsequent extension standards define several standardized methods for a client to authenticate: [1, 3]
________________
1. Shared Secret Methods (Password-Based)
These methods rely on a Client ID (public identifier) and a Client Secret (private password) generated during application registration. [4, 5]
* client_secret_basic (HTTP Basic Authentication):
The client combines the client_id and client_secret into a single string formatted as client_id:client_secret, encodes it using Base64, and transmits it via the standard HTTP Authorization header. [1, 3]
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

* client_secret_post (Form-Encoded Body):
The client includes the client_id and client_secret directly as parameters within the HTTP POST request body. While widely supported, it is generally less recommended than client_secret_basic because the secret sits in the request payload. [2, 6]
POST /token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=YOUR_ID&client_secret=YOUR_SECRET

________________
2. Private Key & JWT-Based Methods (Assertion-Based)
Instead of sending a static secret over the network, the client proves ownership of a cryptographic key. [3]
   * private_key_jwt (RFC 7523):
The client generates a local asymmetric key pair (RSA or EC) and registers the public key with the authorization server. When authenticating, the client constructs a JSON Web Token (JWT) containing claims like issuer, subject, and expiration, signs it with its private key, and sends it in the client_assertion parameter. The authorization server validates it using the registered public key. [3]
   * client_secret_jwt:
Similar to the method above, but the JWT is signed with a symmetric key derived from the client_secret using an HMAC algorithm (e.g., HS256). [3]
________________
3. Mutual TLS (mTLS) Authentication
      * tls_client_auth (RFC 8705):
The client authenticates using a trusted X.509 certificate during the initial TLS handshake with the authorization server. The server verifies the certificate chain or matches a pre-registered Subject Distinguished Name (DN). This eliminates the need to pass any application-layer secrets or tokens during the request body or headers. [1, 3]
